# PostgreSQL historical-cron durability

Bounded historical cron now writes its PostgreSQL custom-table effects and advances
`last_synced_block` in one transaction. A checkpoint is valid only under the
versioned protocol and the *same unchanged schedule*. The guarantee applies to
committed PostgreSQL table effects, not RPC request counts, chain reorganizations,
ClickHouse, downstream publications or live cron.

Historical batches prepare all required RPC inputs before writing. PostgreSQL
then applies each scheduled block in ascending order and, within each block,
executes `cron[].operations` in declaration order. Single-operation INSERT
backfills combine sampled rows into one batched COPY; eligible UPSERTs with
only last-value assignments or non-null scalar counters also use a grouped
statement. UPDATE, DELETE, mixed operations, and unsupported aggregation shapes
retain the sequential path. Both paths keep the same PostgreSQL transaction.
All effects in a batch and its checkpoint commit together: a later operation
failure rolls back preceding operations and progress. Replaying an already checkpointed block performs
no writes. ClickHouse follows declaration order but retains its existing
non-transactional, best-effort checkpoint semantics.

For existing ClickHouse historical schedules with multiple operations, this
changes forward behavior: earlier versions applied the first operation to every
prepared row. Stop writers and review affected rows and progress before resuming;
reconcile or rebuild them as appropriate for the schedule.

## Supported deployment

The initial durable profile admits **one PostgreSQL destination** with one
historical cron entry, **one or more declared operations**, **one nonzero static address**,
an explicit `start_block` and fixed inclusive `end_block`. It rejects mixed
PostgreSQL/ClickHouse writes, factory contracts, static address arrays,
duplicate contract `details` for one network, `cross_chain: true`, and
destinations shared with any other declared custom-table writer (including
event-driven and live-cron tables). It also rejects `timestamp: true` and
synthetic historical timestamp/hash inputs. The physical destination is
checked across all prepared declarations, including schema overrides.
Use stop-before-start upgrades and keep the sampled history stable; reorg recovery
for cron effects is not supported.

## Schedule certificates (protocol version 2)

Every new PostgreSQL historical-cron checkpoint is bound to a canonical JSON
descriptor and its Keccak-256 fingerprint. The descriptor is built from the
resolved table/physical columns and destination, chain ID, network, static
source address, inclusive sampling start/end and normalized block interval,
ordered operations/inputs, column defaults, nullability and table keys.
Declaration order is significant. Unrelated YAML key ordering, RPC endpoint
selection, view-call concurrency, logging and runtime batch size are not.

Both startup and the scheduler verify the certificate. Startup rejects a
mismatch **before** schema synchronization, migrations or `drop_each_run`.
The writer verifies again under the checkpoint row lock, including after
uncertain COMMIT. A mismatch reports the first differing descriptor field.
Changing source, chain ID, grid, operation values/order or destination requires
an independently reviewed migration or coordinated rebuild. The physical
checkpoint name still uses the cron's numeric manifest position; renaming
does not authorize reusing incompatible progress.

## Upgrade and recovery

1. Stop *all* processes and services that can write the affected table, including
   older rindexer images. Take a consistent PostgreSQL backup of the destination,
   checkpoint table and other applicable state before making changes.
2. Inspect the destination and its
   `rindexer_internal.<generated_schema>_<table>_cron_<index>` checkpoint.
   Historical checkpoints from older binaries were not committed atomically with
   their effects. A positive number does not prove completeness; zero was also
   used to mean “not started.” Neither value can be promoted automatically.
3. **Preferred: rebuild.** In a controlled maintenance transaction or offline
   migration, remove the *affected destination contents and checkpoint table
   together*, preserving a backup. Run normal schema setup against the now-empty
   destination to create the versioned checkpoint, initially
   `last_synced_block = NULL` and `protocol_version = 2`, with a canonical schedule descriptor and fingerprint. Replay from the
   trusted declared start block, then verify rows and completed progress.
   Do not truncate a destination shared with other writers or networks.
4. **Alternative: reconcile.** Independently verify the complete ordered
   historical operations against the stored rows and progress. Only a
   schedule-specific reviewed migration may certify protocol version 2 with its matching descriptor and fingerprint.
   Never stamp legacy progress from the current manifest alone: the historical computation must be proven independently. No automatic adoption flag exists.

Versions 1 and 2 distinguish `NULL` (no sample committed) from `0` (block zero committed). Version 1 is now uncertified because it lacks a schedule identity. A missing row is **not** `NULL`: setup and indexing refuse it. An
existing checkpoint table is never automatically reseeded when a network row is
missing, even if the destination currently appears empty. If the checkpoint
table itself is missing, initialization is allowed only with an empty destination.
With surviving effects, startup fails until the destination and checkpoint are
restored or rebuilt consistently. **The converse also fails:** a missing
destination with an existing historical-cron checkpoint is rejected *before*
`CREATE TABLE IF NOT EXISTS` can recreate it. Even an empty destination may
have legitimately completed earlier samples, so an empty table is not evidence
that a non-NULL checkpoint can be trusted. A newly added network similarly
requires an explicit initialization or migration; a redeploy does not silently
add a row.

Never fix a missing checkpoint by inserting `NULL`, increasing `protocol_version` or copying a fingerprint from the current manifest alone. An additive operation or append-only insert could
then be applied twice. Conversely, advancing progress without effects skips
required work. If a transaction's commit reply is lost, the scheduler rereads
locked durable progress rather than trusting the client response.

## Runtime supervision

Startup owns the required cron scheduler's task handle. It observes that
handle concurrently with historical indexing, live indexing and GraphQL:
a failed cron task or a worker panic terminates the startup operation with
an error. Startup cancels the existing indexing-generation token, requests
coordinated shutdown, and makes health readiness fail. Shutdown draining is
bounded so a stuck worker cannot indefinitely suppress the original error.
A bounded cron task that succeeds may finish while persistent services
continue running. If startup fails first, it cancels its outstanding cron
task rather than leaving an independent writer detached.

Live cron retries a failed tick within its existing retry budget. Once
that budget is exhausted, the worker returns a terminal error to the
scheduler and startup supervisor rather than merely logging and running
another tick. Deliberate shutdown remains a normal cancellation path.
These lifecycle guarantees do not make live-cron writes atomic or replay-safe.

## ClickHouse fixture and failure semantics

The ClickHouse historical-cron path is deliberately not part of the
PostgreSQL atomicity guarantee. The existing dynamic ClickHouse UPDATE and
UPSERT writer emits INSERTs into ReplacingMergeTree. It does **not** apply
PostgreSQL-style `add` or `subtract` arithmetic to existing values. For a
single sampled block, the real-server tests apply two `set` assignments to
one logical key and read the resulting row with `FINAL`. A server-side
constraint rejects the second assignment in a separate test: the first
INSERT remains committed, while the historical progress table is unchanged.
Retrying the failed sample can therefore repeat ClickHouse effects. DELETE
uses ClickHouse mutation semantics and is not covered by these ordering tests.

The rootless runner uses a private, disposable ClickHouse service on the
existing Compose fixture network, without giving the test process a Docker
socket. Select an **already local** immutable image ID or repository digest:

```bash
CLICKHOUSE_IMAGE=sha256:<64-hex-image-id> make tests/cron-clickhouse/fixture
```

The target compiles tests offline before starting ClickHouse, never pulls
images, and tears down its project. It passes
`RINDEXER_TEST_CLICKHOUSE_URL=http://clickhouse:8123` to tests, which
create unique database and checkpoint names. Native executions without that
variable use Testcontainers; an invalid supplied endpoint fails rather than
silently falling back to Docker.

The regression suite checks INSERT and arithmetic UPSERT behavior,
checkpoint failure after staged effects, ordered multi-operation replay and
rollback on a later operation, lost checkpoint or destination startup,
completed block zero, legacy rejection, conflicting destination
ownership, duplicate network details, concurrent attempts, and a
real PostgreSQL COMMIT acknowledgement suppressed by the shared wire fault
proxy. These checks do not replace production-image qualification with an
actual manifest and database. No exactly-once claim is made for live cron.
