# Fork changes & migrations

This is the maintained documentation section for
[`numpde/fork-of-rindexer`](https://github.com/numpde/fork-of-rindexer).
We maintain this section, the fork migration notes linked below, and the fork's
[changelog](/docs/changelog). The rest of this site is an **unmaintained snapshot
of inherited upstream documentation** and may not describe this fork correctly.

New documentation will cover differences from upstream here, rather than keeping
a second general-purpose manual up to date. For general background, consult the
[upstream documentation](https://rindexer.xyz); check this section for differences
before applying that guidance to the fork.

## Typed predicate admission for arithmetic recovery

Operations reversed from raw history now validate their predicates during
recovery-plan preparation, before indexing. Event-dependent ABI `string` inputs
are rejected: forward filters apply Unicode lowercase conversion and may parse
numeric-looking strings as numbers, while database text comparisons do not have
the same semantics. A SQL `LOWER()` or `citext` substitution alone would not prove
equivalence. Use a source event carrying a verified numeric/boolean admission
field with an equivalent predicate, or maintain the aggregation outside this
raw-history recovery path. Journal-only operations use their recorded applied
contributions and do not need this predicate reevaluation.

ABI `address`, `bytes`, and `bytes32` predicate inputs are also rejected. Forward
filters evaluate their hexadecimal strings using value-dependent numeric
conversion; native SQL address or byte comparisons do not establish equivalent
admission. This restriction applies to variable-to-variable comparisons too,
even when the predicate contains no literals.

Every referenced event input must have a known scalar source type. Arrays must
select a supported scalar leaf. Public callers of conditional arithmetic rollback
tasks must populate `DerivedTableRollbackPlan::try_add_operation` with the source
types and call `execute_with_rollback_plan`; the untyped `execute` shortcut remains
usable for unconditional operations and predicates using only known transaction
metadata. Direct tuple-array component types use dotted declaration paths such as
`items.amount`, without array indexes.

Execution applies the same checks to legacy plans before committing changes to
raw rows, effects, receipts or cursors. A refusal leaves recovery unfinished; it
does not repair existing orphaned or missing effects. Verify and reconstruct
already-damaged state from canonical history with coordinated journals, receipts
and cursors before reuse. Constant predicates are evaluated by the same Rust
filter evaluator as forward processing, preserving Unicode and numeric-string
semantics without database collation assumptions. Constructors use the filter
parser, so quoted literal text can include SQL keywords or punctuation as data;
unparseable SQL is rejected rather than passed to a SQL token blacklist.
String literals and quoted syntax in event-dependent raw-history predicates
remain unsupported, including constant string clauses combined with an event
condition. Validation inspects the parsed expression, so unquoted hexadecimal
literals are included: `$value > 0 && 0x00 == 0x0` is rejected even though it has
no quote characters. Forward evaluation treats both hex values as numeric zero,
while the SQL strings would differ. Fully constant `0x00 == 0x0` still evaluates
to true using the forward evaluator. Use
unquoted scalar paths and typed numeric/boolean values only when the rewrite
preserves the intended meaning. Fully constant predicates and journal-only
predicates retain their separate evaluation paths.

## Compound event predicates

Forward table predicates retain ABI component names through nested tuples,
dynamic/fixed arrays and `iterate` aliases. For example, `$data.info.amount`
and `$item.amount` address the same named components used by recovery planning.

Older callbacks could commit raw rows and application receipts while a valid
named-field predicate silently skipped its derived effect. Correcting the
expression does not retry those committed receipts. Reindex affected canonical
history with coordinated derived state, journals, receipts and cursors.

PostgreSQL recovery resolves direct tuple-array paths such as
`$items[0].amount`, `$items[0].info.tokenAmount` and `$items[0].amounts[0]`
through JSONB, then casts the scalar leaf using its ABI type. This also applies
to fixed-size tuple arrays. Intermediate objects and arrays retain their JSON
shape until the leaf is extracted; native SQL arrays use their existing indexing.

Journal recalculation quotes derived column identifiers in assignments, extrema
updates and record-field access. Supported names such as `order` no longer fail
PostgreSQL recovery after successful forward writes. Upgrade and retry a pending
rollback caused by this syntax error; the column does not need to be renamed.

## Physical destination ownership during recovery

A derived destination participating in reorg recovery requires one manifest
`Table` declaration. Validation resolves the same `database:` override and
normalized table name used by runtime writes before applying recovery rules.
It covers contracts and native transfers, explicit/default-schema aliases, and
PostgreSQL identifier truncation and quoted schema aliases. Truncation uses the
standard 63-byte limit and drops any UTF-8 character crossing that boundary,
including names supplied by writers whose own source has recovery disabled. In
projects with reorg handling, `database:` must identify one schema; database-qualified
schema paths cannot be resolved safely during offline validation. Recovered
identifiers must use lowercase so quoted writes and bare recovery SQL address the
same catalog object.

Separate declarations cannot hide a partial assignment group, a set/arithmetic
mixture, an insert/mutable mixture or a missing extrema baseline from each
other's local checks. Recovery currently merges plans by destination without a
complete cross-declaration write model; startup therefore refuses shared recovered
targets and names the destination and all declaring owners. This applies when
any participating source enables recovery, including aliases whose own source
has recovery disabled. The existing operation restrictions run once at this
physical ownership boundary.

One declaration can still watch multiple addresses and networks. Tables with the
same basename in different schemas, or different names in one schema, remain
independent. Shared destinations without reorg handling retain their behavior.
For recovered data, consolidate into one declaration only when it represents the
complete write model and satisfies every recovery rule, or choose distinct
physical destinations. Do not remove a declaration merely to hide its existing
history: reconstruct conflicting derived state and journals with coordinated
receipts and cursors before reuse. No automatic shared-history migration is
attempted. This is manifest ownership, not distributed writer fencing.

## Arithmetic predicates and recovered tables

Mutable tables on a reorg-enabled network now reject arithmetic expressions in
`if` and its legacy `filter` alias. This includes division, addition, subtraction,
multiplication and exponentiation, for contract and native-transfer tables.
Forward filters evaluate checked unsigned integers; SQL division returns a
fraction, and SQL overflow/error behavior also differs. Recovery cannot safely
use that SQL predicate to decide which source effects actually occurred.

Use verified equivalent comparisons. For example:

```yaml
if: "$rindexer_block_timestamp >= 1000 && $rindexer_block_timestamp < 2000"
```

This expresses the integer predicate `$rindexer_block_timestamp / 1000 == 1`.
Logical combinations of comparisons remain supported. Arithmetic characters
inside string literals are not interpreted as arithmetic. Non-reorg predicate
arithmetic, insert-only filters and existing value expressions retain their
behavior; insert-only recovery deletes rows by provenance without reevaluating
the filter.

Public and legacy `DerivedTableRollbackOp.condition` values must also parse as
event-filter expressions. Recovery no longer accepts an unparsed raw SQL
fallback, even when the SQL token safety validator accepts it. For example,
`value = 1` must be expressed as `$value == 1`. SQL casts such as
`value::NUMERIC > 7` must be rewritten using the supported event field and its
source type; verify equivalence rather than deleting a cast blindly. Arithmetic
such as `value / 1000 = 1` cannot bypass the restriction by using SQL equality.
Parse failures stop recovery with the offending predicate and a filter-syntax
instruction. Token safety alone does not establish forward evaluation semantics.

Legacy recovery plans containing arithmetic now return an explicit error before
permanent raw data, receipts, effects or cursors change. Verify the rewrite and
source metadata before retrying recovery; changing a predicate to a different
meaning does not repair previously indexed effects. General SQL emulation of the
forward integer evaluator is deferred rather than approximated operator by
operator.

## Complete assignment groups for recovered rows

On a reorg-enabled table, every mutable operation must supply every non-key column
that any operation writes with `action: set`. A table with assignment columns
`x` and `y` therefore cannot accept one upsert/update setting only `x` and another
setting only `y`. The same check applies to native-transfer tables and to an
arithmetic operation that omits a table's assignment columns. Arithmetic-only
and insert-only tables are unchanged; non-reorg partial assignments remain valid.

Forward admission orders the entire row. An older partial upsert can be correctly
superseded while its canonical candidate remains journaled. Independent column
reconstruction can then install its rejected assignment during an unrelated
rollback. Discarding superseded candidates would instead lose the state needed
when the newer version is orphaned. The current journal does not retain complete
row versions or independent per-column admission, so startup now rejects this
unsupported history with the table and omitted assignment columns in the error.

Combine assignments only when the source provides a complete version of the
assignment group, or split independent state into separate keyed tables and adapt
queries. Adding missing assignments with default values changes forward behavior
and is not a migration preserving the old partial-write semantics. Complete
assignment groups retain superseded candidates for rollback; this restriction
does not change non-reorg ordering.

There is no journal schema migration in this change. Editing YAML does not make
old partial-write history complete. Before reusing such history under a new
model, reconstruct derived state and journals from verified canonical sources,
coordinating receipts and cursors so replay is not suppressed. This is required
even if no incorrect rollback has been observed. Automatic support for partial
recovered assignments is deferred until whole-row versions or consistent
per-column versioning can preserve their admission semantics.

## Timestamp predicates during recovery

`$rindexer_block_timestamp` in a table condition means numeric Unix seconds in
both forward indexing and recovery. PostgreSQL raw timestamps retain their
`TIMESTAMPTZ` representation; recovery extracts epoch seconds for the predicate,
without changing timestamp-typed keys or the database schema.

When required table inputs fetch a missing timestamp from a hash-matching header,
the callback now persists it with the raw PostgreSQL row in the same transaction
as receipts and derived effects. This also covers events whose condition is false:
reconstruction needs the timestamp to make the same admission decision later.
Older raw rows with missing required timestamps are not backfilled by this change;
verify and repair their source metadata before relying on timestamp-filtered
recovery. Restart alone cannot hydrate an event already suppressed by a receipt.

## Network-wide rollback coverage

A detecting subscription can lag behind other subscriptions on the same network.
The coordinator now holds the exclusive network writer barrier while resolving
the rollback endpoint from retained header coverage and the greatest committed
height across its registered raw event tables. It keeps that endpoint for recovery
retries and notifications. Raw events, receipts, arithmetic reversal, journal
invalidation and insert-only cleanup use the same inclusive range.

This prevents a faster subscription's receipts from surviving after its effects
have been invalidated. Providers must supply canonical headers for the full
resolved range; a failed proof leaves recovery pending and writers fenced.
Existing mismatches created by older rollback code still require verified repair;
this change does not reconstruct effects suppressed by already-retained receipts.

## Runtime lifecycle integration check

After building an image separately with `make runtime/image/build`, run:

```sh
make MAKE_TIMEOUT=8m runtime/lifecycle/checks RINDEXER_IMAGE=sha256:...
```

Use the immutable local image ID printed by the build. The check requires the
pinned PostgreSQL and Anvil images to be present; it never builds or pulls images.
It uses the local rootless Docker context named `rootless` by default. Set
`RINDEXER_DOCKER_CONTEXT` to select another local rootless context. The selected
Unix socket is resolved once and used for rendering, execution and cleanup;
ambient Docker and Compose overrides are discarded.

The self-contained `Funded` ABI and event emitter live in this repository. The
check starts the actual indexer image, backfills an event, catches up after
indexer downtime, replaces a block on local Anvil, and restarts again. Every
phase requires the expected raw rows, funding total, provenance, application
receipt count, orphan removal and durable health cursor with zero lag. Large
amounts exceed 64-bit range. This tests indexing, not PayToPlay payment logic,
and reads no sibling checkout. A historical image can be supplied to reproduce a
regression; the result records its image ID and revision label when present,
rather than assuming it was built from the current checkout.

The host runs only the Python standard-library orchestrator and Docker client.
The disposable services run as non-root users with read-only root filesystems,
dropped capabilities, and a combined one-CPU budget. PostgreSQL and Anvil have
no published ports; health uses a temporary loopback port. A unique Compose
project owns its database volume, which is deleted on success, failure or handled
cancellation. Teardown failure fails the check and prints the recovery command.
The runtime profile retains its routable RPC bridge; configured endpoints are
local fixtures, but this check does not restrict internet egress. No engine socket
or checkout is mounted into the containers. `MAKE_TIMEOUT` bounds the full check
and reserves the existing cleanup grace period.

## Historical-to-live cursor identity

A subscription keeps its configured `start_block` as part of its durable cursor
identity when it switches from historical to live indexing. Its runtime resume
position does not create a second cursor. PostgreSQL live writes, restart catch-up
and health therefore read the same checkpoint. When saved progress is zero,
PostgreSQL startup uses the configured start rather than a later historical hint.
Handlers without PostgreSQL retain the in-process historical resume hint.

Existing shadow cursors created by earlier handoffs are not merged into the
configured cursor: their maximum does not prove contiguous canonical coverage.
An upgrade may replay an already indexed range under the configured identity;
PostgreSQL application receipts suppress previously applied effects. This change
does not repair skipped or noncanonical history behind a durable checkpoint.

## Derived recovery with separate column operations

PostgreSQL recovery now restores a column's database default (or NULL for a
nullable column without a default) when all of that column's journal entries are
orphaned but the row has a surviving canonical contribution. This defensive
fallback handles stored histories where a creator left another column at its
default; it does not establish that partial assignment histories are safe.
New manifests must satisfy the complete assignment groups described above.
The internal fallback also handles empty `max`/`min` journals. New manifests must
meet the extrema admission requirements below; the fallback alone cannot recover
an omitted creation baseline when journal operands survive.

The fix preserves the canonical row's sequence and provenance. It does not repair
state left wrong by an earlier completed rollback; review affected ranges and
coordinate canonical repair with derived state, journals, application receipts
and cursors.

## Insert-created rows and reorg recovery

A derived table on a reorg-enabled network must not mix `insert` with `upsert`,
`update` or `delete`. Startup now rejects this previously accepted configuration,
including tables under `native_transfers`. Recovery cannot reliably reconstruct
an insert-created baseline after reverting a later mutation; it could previously
delete a canonically created row.

Use keyed `upsert` operations for mutable state, or move append-only `insert`
operations into a separate table. Review the intended key and duplicate semantics
when changing an insert to an upsert. Insert-only tables, mutable-only tables and
mixed tables on networks without reorg handling retain their existing behavior.

For an existing deployment, stop the writer and verify affected canonical ranges
before resuming. Changing the manifest does not repair a row lost in an earlier
rollback. Coordinate any required rebuild with derived state, recovery journals,
application receipts and cursors; see the [sequence-ordering migration](/docs/migrations/sequence-ordering).

## Hanging destinations with durable delivery

With `delivery_guarantee: at_least_once`, a hanging publisher now receives a
persisted retry delay instead of immediately blocking the next eligible route.
The admitted delivery attempt remains bounded to 30 seconds. The worker stops
waiting for publishers five seconds before that deadline to leave time for
PostgreSQL deferral or acknowledgement. Time waiting for the delivery lease or recovery barrier is
outside this budget and remains cancellable during shutdown or recovery.

Healthy destinations can then progress while the hanging destination remains
pending. Expired retries rejoin the queue at their retry time, behind older
untouched obligations of the same recovery priority. Later records for that same destination still wait for its earlier
record. A timeout cannot establish whether the destination accepted a message;
retries retain the same message ID, so consumers should deduplicate it. If the
database cannot commit the retry delay, durable database state determines the
next attempt. This changes no best-effort delivery configuration.

## Extrema need a journaled creation baseline

On reorg-enabled tables, every `upsert` that can create a row must initialize each
`max`/`min` column using that same extrema action. All writes to that column must
use the same action. Update-only extrema and a mix of `set`, arithmetic, `max`
or `min` on one column now fail startup. These checks cover contract and native-transfer tables.

A default is not a substitute for creation history. If arithmetic creates a row
with default 42, a later `max(20)` retains 42, but journaling only 20 loses that
baseline. Conversely, a first `max(20)` can create a row at 20 despite default 42;
always folding the default into recovery would also be wrong.

For a fixed baseline of 42, each creator can explicitly journal
`{ column: extreme, action: max, value: "42" }` (use `min` for a minimum).
That records the baseline as a source contribution at creation. Literal extrema
operands are supported because they are journaled; the arithmetic restriction
below applies to reversible actions.

Keep monotonic extrema in a table whose creators journal their initial operand,
or split unsupported operations into separate tables. Adding an extrema action
to a creator can change its initial value: review that behavior before migrating.
Changing YAML does not repair old journal history or earlier incorrect rollbacks.
Rebuild affected derived state and recovery journals from verified canonical
history, coordinating application receipts and cursors as described in the
[sequence-ordering migration](/docs/migrations/sequence-ordering).

## Deletes require row reconstruction

`delete` now fails startup on reorg-enabled derived tables, including native-transfer
tables. An orphan delete can remove a row created by a canonical upsert. Recovery
has no complete deletion before-image and cannot recreate that row.

Retain the row and update a journaled status field, filtering it in downstream
queries, or move deletion outside the recovered table. A status update changes the
storage model: review consumers that previously expected the row to disappear.
Deletes on networks without reorg handling retain their existing behavior.

This restriction prevents new accepted delete histories; it does not restore rows
lost during an earlier rollback. Verify affected canonical ranges and coordinate
any repair with derived state, journals, application receipts and cursors.

## Reversible arithmetic operands

On reorg-enabled mutable tables, `add` and `subtract` require a single event-field
operand such as `$value`. Literal and computed operands now fail startup; they
were not reliably represented in the rollback plan. The planner also rejects an
unsupported operand rather than silently omitting the operation.

For unit counts, use `increment` or `decrement` with `value` omitted or set to
`"1"`. Other explicit counter operands now fail startup because their recovery
counts events rather than summing arbitrary amounts. For non-unit constants, use
a supported event-field value or move the aggregation outside the recovered table.
Review semantics before replacing an arbitrary amount with a unit counter.

These checks cover contract and native-transfer tables. Recovery plans are built
only for reorg-enabled networks, preserving literal arithmetic on other networks.
Insert-only tables retain their existing behavior. Editing YAML does not repair
state previously lost through an incomplete rollback plan: coordinate any verified
canonical rebuild with derived state, journals, receipts and cursors.

## Multiple derived writes from one event

PostgreSQL event application now orders work by event position before manifest
operation order. Multiple writes from one event may continue at its sequence only
when PostgreSQL identifies the existing row version as written by the active
event transaction and its sequence, block hash, transaction hash and contract
address match. Committed equal-position rows and different events retain the
strict ordering protection. Application receipts still suppress event replay.

Multi-operation mutable batches execute per input to preserve this order, which
can issue more SQL statements than the former operation-first batching.
Insert-only batches and single arithmetic upserts that need no recovery journal
retain batching. Updates always check each input individually; journaled
operations follow the rules below. The sequence encoding and schema do not change.

An event whose second effect was previously skipped may already have a receipt.
Upgrading does not replay it automatically. Verify affected ranges and coordinate
canonical derived-state repair with journals, application receipts and cursors.

## Recovery candidates and actual writes

PostgreSQL distinguishes applied inputs, sequence-superseded upserts and rejected
inputs. An unguarded `upsert` defines a canonical state version even when a newer
live row wins the sequence comparison. That version remains in the journal so
rollback can recover it; recording the candidate does not replace newer live state.

An `update` against a missing target and an input rejected by a SQL table-state
guard contribute no recovery entry. Their valid raw events and receipts can still
commit: an UPDATE that matches no row is a configured no-op. Reorg-enabled tables
already reject SQL table-state guards at startup.

Journaled inputs execute individually in event order. This also prevents a
rejected older operand from being aggregated into an admitted newer UPDATE.
When several applied `set` writes share one event position, the journal ID
breaks ties so recovery selects the last applied write.
The same rule applies to eager per-operation PostgreSQL writes; their existing
commit boundary is unchanged. Journaled batches may issue more SQL statements,
and PostgreSQL table logs report affected rows.

Old phantom journal entries are not removed automatically. Verify affected ranges
and rebuild derived state and journals together with receipts and cursors before
relying on recovery. No journal schema migration is introduced by this change.

## Arithmetic updates require applied-effect history

Reorg-enabled derived tables now reject `update` operations containing `add`,
`subtract`, `increment` or `decrement`. Contract and native-transfer tables use
this same startup check. Recovery currently derives arithmetic contributors from
raw events, which cannot distinguish an update that found no row from an applied
delta. For example, a skipped canonical update must not keep a row alive after
rollback removes the orphaned upsert that actually created it.

Use arithmetic `upsert` only when creating a missing row is intended. This changes
creation semantics and is not an automatic replacement for `update`. Otherwise,
keep that aggregation outside the recovered table until durable applied-effect
tracking is supported. Non-arithmetic updates retain their existing admission
rules; this restriction does not change arithmetic upserts.

On networks without reorg handling, arithmetic updates remain supported. Every
PostgreSQL update input now checks its target and sequence individually, even
when it is the only prepared operation. A batch containing an older rejected
`add(100)` and a newer accepted `add(1)` therefore changes 10 to 11, matching
separate callback execution. Receipts continue to suppress replay. This can issue
more SQL statements than aggregating deltas before admission.

## State replacement and arithmetic on one column

Reorg-enabled tables now reject `set` combined with `add`, `subtract`, `increment`
or `decrement` on the same column. This applies across operations and event
mappings, including native-transfer tables. Recovery cannot reconstruct the
ordered replacement/accumulation history from the current journal model.

For example, a canonical add can establish 10 and an orphan set can replace it
with 20. Removing the set journal must not reset the surviving arithmetic value
to its configured default. Startup now prevents that unsupported history.

Use separate columns/tables for replacement state and accumulated amounts, or one
update model for the column. Different columns may still use different actions
when every mutable operation supplies the complete assignment group described
above. Networks without reorg handling retain their existing behavior. Editing YAML does
not repair earlier incorrect rollbacks: coordinate verified canonical repair of
derived state and journals with application receipts and cursors.

## PostgreSQL transaction-identity compatibility

The same-event continuation query now uses the transaction-ID API available on
both the native PostgreSQL 11 fixture and the prepared PostgreSQL 16 fixture. It
reduces the epoch-extended ID to the 32-bit transaction ID stored in tuple `xmin`.
The ownership regression checks both the active transaction and a later
transaction observing the committed row. Existing configurations need no
PostgreSQL version upgrade for this fix.

## Out-of-order upsert versions

Independent streams can deliver block 100 before canonical block 99. A later
`upsert set(20)` from block 99 must leave block 100's live value 30 intact while
retaining its canonical version. If block 100 is then orphaned, recovery restores
20 with block 99's provenance, and its application receipt remains committed.

This differs from a missing-row UPDATE, which neither creates a row nor defines
an unconditional replacement version. Recovery candidate selection follows that
operation distinction rather than treating every zero-row SQL result alike.

## Cross-chain source identity and manual upgrades

Tables with `cross_chain: true` now store the source `network` on each
row in PostgreSQL and ClickHouse. It remains outside the shared primary key.
Rolling back chain A removes only A's rows at or beyond its fork; chain B's
independent heights do not define A's recovery boundary.

With table creation enabled, existing PostgreSQL tables missing this required,
non-null source column stop startup with a clear error. Automatic migration is deferred: neither a default
network nor a block number can recover the chain that produced an old row.
An existing deployment must reconstruct the rows from canonical events with
source-network identities, coordinating receipts and cursors so replay is not
suppressed. Manually managed ClickHouse tables also need their source column
before writing with this version; ClickHouse reorg recovery remains unsupported.
`disable_create_tables: true` also bypasses setup-time schema checks: manually
managed tables must already provide the required source column before use.

The passing `known_risks::known_risk_cross_chain_legacy_schema_requires_manual_rebuild`
test records this operational limitation. It asserts the explicit startup error
for missing or nullable provenance and preservation of existing raw history.
When an automatic migration can establish source identities, replace this test
with migration-success coverage. It is not an ignored test or a claim that the
legacy table is safe to recover.

## Equal positions in shared PostgreSQL rows

Shared rows compare `(block number, transaction index, log index)` first. When
positions are equal across chains, the bytewise greatest configured network name
wins (`COLLATE "C"` in PostgreSQL). This is an explicit tie-breaking policy, not a
claim that block heights measure time across chains. Both forward admission and
journal/metadata recovery use the same policy, independent of arrival order.
Multiple writes from the same event still follow manifest operation order.

The source `network` is stored as row provenance, outside the shared key. Inputs
for shared tables execute individually, including arithmetic upserts, to preserve
ordering of state fields and metadata. Arithmetic amounts still combine admitted
contributions; this tie-breaker selects state-setting fields and provenance.
Non-shared tables retain their existing event-position order.

Existing cross-chain state must be rebuilt with canonical source identities and
this ordering rule. A newly added column cannot by itself correct values selected
under the old first-arrival rule. Automatic migration remains the known limitation
above; coordinate any rebuild with journals, receipts and cursors.

## Source-network timestamp recovery

A shared arithmetic row can retain contributions from another network after a
rollback. When a surviving raw event lacks its timestamp, recovery now looks up
that event's network in the running generation's provider registries. It checks
the returned header against that contribution's block hash before using its time.
Contract-event provider maps and native-transfer providers both participate.

A missing provider or mismatched hash stops rollback with an error identifying
the source network and block. The transaction leaves derived values, provenance,
raw events, receipts and cursors unchanged; it does not substitute the reorging
network's header at the same height. Keep a provider capable of serving retained
source history when shared rows may require this enrichment. No additional
migration or journal schema is introduced by this timestamp fix.

## Recovery comparison domains and source storage

Raw-history arithmetic recovery admits unsigned integer and Boolean comparisons.
Boolean operands require `==` or `!=` with another Boolean. Numeric literals must
fit an unsigned 256-bit integer. Signed event inputs and fractional, negative or
out-of-range literals are refused because forward filtering can reject them
according to operand values and order. Constant-only predicates retain the actual
forward evaluator, and journal-only operations retain their applied-effect history.
Use a verified unsigned/Boolean admission field or keep the aggregation outside
raw-history reconstruction; changing a condition is not a historical migration.

Missing array elements remain errors through left-to-right logical evaluation;
a later true OR operand cannot admit a contribution that forward processing skipped.
Rollback source casts preserve unsigned 64-bit values without narrowing to BIGINT.
Fixed primitive arrays retain their native array representation. Indexed complex
ABI inputs remain topic hashes, not recoverable arrays or tuples.

Stop writers and reconcile previously affected raw events, derived state, journals,
receipts and cursors together before reuse. These corrections do not repair old
incorrect reversals or effects skipped under an earlier predicate.
