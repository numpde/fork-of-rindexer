# Health Monitoring

Rindexer includes a comprehensive health monitoring system that provides real-time insights into the status of your indexing infrastructure. This built-in monitoring helps you ensure your indexers are running smoothly and quickly identify issues when they occur.

## Overview

The health monitoring system tracks the status of key components:

- **Database connectivity** - PostgreSQL connection health
- **Indexing status** - Whether the indexer is running and active task count
- **Sync status** - Data synchronization health across storage backends
- **Overall system health** - Aggregated status across all components

## Terminal indexing failures

A terminal contract-event fetch error, unexpected producer exit or callback-task failure makes `/health` return HTTP `503` with `services.indexing: "unhealthy"` and an entry in `indexing.failed_streams`. The entry identifies the indexer, contract, event and network; it does not expose callback or RPC error text. For stream-level and generation-stop failures its numeric bound fields describe configuration, rather than an exact failing event position; an unspecified bound is `0`. The subscription catalog exposes configured bounds as nullable fields.

Failures become visible before already admitted callbacks finish draining. Reporting an operational failure does not abort those handlers. The generation supervisor inspects both task and application results as each stream finishes, requests a cooperative generation stop on the first failure, waits for remaining tasks to settle, and returns that failure. Finite successful streams do not stop their live peers.

A blocked or indefinitely retrying user handler can delay final cleanup; failed health is available during that wait. Stop the failed instance completely before starting its replacement. Custom-handler effects retain their existing replay requirements.

## PostgreSQL subscription progress

The runtime supplies health with the same contract and native-transfer registries used for indexing. PostgreSQL health reads each configured query's `(network, cursor_key)` checkpoint; an unrelated raw table or legacy network-only cursor is not evidence of its progress. `indexing.subscriptions` includes the indexer, contract, event, network, query key, configured bounds, `last_synced_block`, `observed_head`, `target_block`, `lag_blocks` and status.

For example, with head `100`, safe distance `2`, and two query cursors at `95` and `80`, their targets are both `98` and their lags are `3` and `18`. Lag excludes blocks before a configured start. Each request reads durable progress again; it does not infer a completed query from another query's maximum.

Subscription states are `waiting_for_checkpoint`, `syncing`, `live`, `completed`, `failed` and `unavailable`. Missing checkpoints report null progress/lag rather than zero. A finite query is `completed` only after its durable cursor reaches the configured `end_block`; catching up to an earlier safe head remains `live`. An unavailable RPC head or checkpoint read produces `unavailable`, null unknown values and HTTP `503`; it is never presented as zero lag. Health samples checkpoint rows and heads independently, not as an atomic cross-network database snapshot.

One RPC head probe per configured network is made per health request, with a two-second timeout per probe. Choose a polling interval appropriate for your RPC budget. Normal catch-up reports `services.sync: "syncing"` while overall health remains a process/connectivity check; a `200` response is not a freshness SLA. Alert on each subscription's lag and status for deployment readiness. ClickHouse/CSV retain their existing storage health checks and do not expose PostgreSQL cursor progress.

Rust callers constructing `HealthServer` directly should attach `.with_event_registry(&registry)` and, when applicable, `.with_trace_registry(&trace_registry)`. A PostgreSQL indexer configured with inputs but no registry catalog reports sync as `notconfigured`, rather than guessing from table existence. No YAML changes are needed for the built-in runtime. JSON clients must allow the additive `indexing.subscriptions` field and the new `syncing` service status.

## Health Server

The health monitoring server runs automatically alongside your rindexer instance on a separate port. By default, it runs on port `8080`, but this can be configured.

### Starting the Health Server

The health server starts automatically when you run rindexer with indexing enabled. No additional configuration is required.

```bash
# Health server starts automatically with indexing
rindexer start indexer
rindexer start all
```

### Health Endpoints

#### GET /health

Returns the complete health status of your rindexer instance.

**Response Format:**

```json
{
  "status": "healthy",
  "timestamp": "2024-01-15T10:30:00Z",
  "services": {
    "database": "healthy",
    "indexing": "healthy",
    "sync": "healthy"
  },
  "indexing": {
    "active_tasks": 2,
    "is_running": true
  }
}
```

**HTTP Status Codes:**
- `200 OK` - System is healthy
- `503 Service Unavailable` - System has issues

## Health Status Types

The health endpoint returns different status types for each service:

| Status | Description |
|--------|-------------|
| `healthy` | Service is functioning normally |
| `syncing` | Selected subscriptions are catching up to their safe targets |
| `unhealthy` | Service has encountered an error |
| `unknown` | Status cannot be determined |
| `notconfigured` | Service is not set up |
| `disabled` | Service is intentionally disabled |
| `nodata` | Service is working but no data is available |
| `stopped` | Service is not running |

## Service Health Checks

### Database Health Check

The database health check verifies PostgreSQL connectivity and functionality:

- **`healthy`**: PostgreSQL is enabled and a simple `SELECT 1` query succeeds
- **`unhealthy`**: PostgreSQL is enabled but the connection fails or query errors occur
- **`notconfigured`**: PostgreSQL is enabled but no database client is available
- **`disabled`**: PostgreSQL is not enabled in the configuration

**What it checks**: Basic database connectivity by executing `SELECT 1` against the PostgreSQL instance.

### Indexing Health Check

The indexing health check monitors the indexer process state:

- **`healthy`**: The indexer is currently running (system state flag is set)
- **`stopped`**: The indexer is not running (system state flag is not set)

**What it checks**: The global `IS_RUNNING` flag that tracks whether the indexer process is active.

### Sync Health Check

For PostgreSQL, sync health uses the registry-selected durable checkpoints and bounded RPC head probes described above. It reports `healthy` for caught-up queries, `syncing` during catch-up, `nodata` when selected checkpoints are missing, and `unhealthy` when a query has failed or its head/checkpoint is unavailable. PostgreSQL connectivity alone does not prove that a selected subscription is advancing.

**For CSV storage:**
- **`healthy`**: The configured directory contains `.csv` files.
- **`nodata`**: The directory or CSV files are absent.
- **`unhealthy`**: The directory cannot be read.
- **`notconfigured`**: CSV storage is not configured.

### Overall Health Status

Database/indexing/sync failures or missing required configuration return HTTP `503`. Normal catch-up (`syncing`) and a new deployment awaiting its first checkpoint (`nodata`) remain process-health `200` states. Use per-subscription lag/status for freshness readiness; table presence is no longer PostgreSQL progress evidence.

## Health Server Lifecycle

The health server's lifecycle depends on which services you start:

### `rindexer start indexer` (with end_block set)
- **Short-lived**: Health server starts with the indexer and **dies when indexing completes**
- **Use case**: Historical data indexing that has a defined end point
- **Health monitoring**: Only available during the indexing process

### `rindexer start indexer` (no end_block set)
- **Long-lived**: Health server starts with the indexer and **stays alive for live indexing**
- **Use case**: Continuous live indexing that runs indefinitely
- **Health monitoring**: Available continuously while the indexer is running

### `rindexer start graphql`
- **No health server**: Health server is **not started** in GraphQL-only mode
- **Use case**: Running only the GraphQL API without indexing
- **Health monitoring**: Not available (health server requires indexing to be enabled)

### `rindexer start all`
- **Long-lived**: Health server starts with the indexer and **follows the GraphQL server lifecycle**
- **Use case**: Running both indexing and GraphQL API together
- **Health monitoring**: Available as long as the GraphQL server is running

## Configuration

### Custom Health Port

You can configure the health server port using the `health_port` setting in your `rindexer.yaml` file:

```yaml
global:
  health_port: 8081
```

## Production Monitoring

### Load Balancer Health Checks

Configure your load balancer to use the health endpoint for health checks:

```
Health Check URL: http://your-rindexer-instance:8080/health
Expected Status: 200 OK
```

### Monitoring Tools

You can integrate with monitoring tools like Prometheus, Grafana, or DataDog to track health metrics and set up alerts based on HTTP status codes and response times.

## Troubleshooting

### Common Issues

- **Health server not starting**: Check if port is in use, verify YAML configuration
- **Database health failing**: Verify PostgreSQL connection and permissions
- **Sync health issues**: Check storage configuration and file permissions

### Debugging

Enable debug logging for detailed health information:

```bash
RUST_LOG=debug rindexer start indexer
```

## Best Practices

- Set up continuous monitoring of the health endpoint
- Configure appropriate alert thresholds
- Keep health check logs for troubleshooting
- Monitor multiple instances if running in a cluster

## API Reference

### Health Endpoint

- **URL**: `GET /health`
- **Response**: JSON with health status and service information
- **Status Codes**: 200 (healthy), 503 (unhealthy)
